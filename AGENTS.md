# Project verification

- Java 21 and Maven are required. Run `mvn -B -ntp verify`; add `-o` only after dependencies and the Surefire JUnit provider are cached. Tests use JUnit 5, AssertJ, and Spring MockMvc.
- Run locally with `java -jar target/astro-backend-1.0.0.jar --server.address=127.0.0.1`. The default port is 18080; `SERVER_PORT` overrides it.
- Build with `podman build --format docker -t astro-backend:1.0.0 .` to preserve the Dockerfile healthcheck. Podman's default OCI format discards image healthchecks.
- Validate Compose with `podman compose -f podman-compose.yml config -q` so expanded environment secrets are not printed. Compose publishes container port 8080 on loopback port 18080; `ASTRO_PORT` overrides the host port.

# Calculation conventions

- Birth input uses fixed IST (UTC+05:30). Both chart services must use the same validated conversion and preserve seconds in UTC and Julian dates.
- Western houses are Placidus; assign planets by actual cusp intervals, including wraparound through Aries. Placidus is undefined at polar latitudes.
- House reference fixtures were generated with pyswisseph 2.10.3.2 `houses_armc`, using the same RAMC and mean obliquity as the Java implementation. This is a verification-only tool, not an application dependency.
- Ashtakavarga reference contributors are ordered Sun, Moon, Mars, Mercury, Jupiter, Venus, Saturn, Lagna. Unreduced BAV row totals are 48, 49, 39, 54, 56, 52, 39; SAV totals 337. Reference tables and the Raman Sun fixture: https://vedastro.org/blog/Mastering-Ashtakavarga-Part-2-Building-Bhinnashtakavarga-Charts.html
- Dasha uses 365.25-day years and a 120-year output window from birth. Compute sub-periods from the full parent before clipping the birth balance. Date-only boundaries use ceiling to retain a nonempty initial partial day, and child intervals must exactly partition their parents.
- The planetary ephemeris remains an approximate Meeus/Kepler implementation, not a high-precision Swiss Ephemeris replacement. Golden house tests do not establish planetary-position accuracy over all dates.

# Advanced Python worker

- The preceding fixed-IST/approximate-ephemeris conventions describe the legacy Java endpoints. `/api/astro/v2` uses explicit IANA timezones, Swiss Ephemeris, and an isolated Python process per request.
- Run worker regression tests from the repo root: `target/engine-venv/bin/python -m unittest discover -s worker -p 'test_*.py' -v`. Maven does not run Python tests.
- The Java worker bridge expects `target/engine-venv/bin/python` and `worker/engine.py` unless configured otherwise; run the jar from the repo root. The current Dockerfile packages the legacy Java application only, not the advanced Python runtime.
- V2 defaults to natal only; select other methods explicitly. Method-specific parameters can be placed in `options`. `name` accepts the JSON alias `fullName`; `gender` is required for Chinese decade/luck direction conventions.
- PyJHora uses local-time Julian days except `sidereal_longitude`, which takes UTC. Initialize its node constants AND `drik.set_planet_list`, restore the Swiss data path after imports, and never allow library configuration to leak between methods.
- PyJHora Shadbala rows are Sthana, Kala, Dig, Cheshta, Naisargika, Drik, total Virupas, total Rupas, ratio. Columns are Sun through Saturn. Ashtakavarga reductions mutate their input; copy BAV rows before reductions.
- V2 Vimshottari uses 365.25-day years, UTC half-open intervals and 120 years from birth. Other exposed PyJHora dashas use the explicitly selected mean-sidereal-year convention and sign-based names where applicable.
- Primary directions currently expose direct/converse planetary conjunctions to MC/IC only, with Naibod or Ptolemy keys. They are not full semiarc or interplanetary directions.
- Zi Wei implements 14 major stars, four auxiliary stars, natal/annual transformations and nominal-age decades. It uses local civil midnight, Lunar New Year and an explicit leap-month rule. Major-star/body/decade placements were compared against iztro 2.5.4 for 99 charts; three permanent chart fixtures and published placement examples are in the worker tests. Node/iztro are verification-only, not runtime dependencies.
- BaZi uses lunar-python 1.4.8: year/month boundaries and Yun intervals are evaluated against solar terms in UTC+08; day/hour pillars use birth-local civil time. No true-solar-time correction is applied.
- Scenario timing windows are Dasha boundaries, with midpoint transit samples, not exact transit event searches. Interpretations are heuristic and have no calibrated probabilities. A `computed` status or successful smoke test is not an independent accuracy check for every method.

# Local AI reports

- `POST /api/astro/v2/ai/report` accepts `birth`, explicit-offset `asOf`, optional `topic` (defaults to `general`), and calculation `options` (`ayanamsa`, `nodes`, `houses`). Reports are detailed by default: 12 chapters, each 250–400 AI narrative words, total 3,000–4,800. `options.reportLength="brief"` explicitly selects the old short summary. Invalid lengths are rejected.
- General detailed reports cover foundations, emotions, career, finances, partnerships, education, home, wellbeing, travel/change, current periods, conflicting interpretations, and practical review. A specified topic produces 12 focused chapters instead. The `prediction` calculation is cached once per topic within a request (8 topics for a general report); caller `methods`, `question`, and `name` are not forwarded to the LLM. This endpoint produces English reports, not conversational chat.
- `report.wordCount` and each section's `wordCount` count AI narrative words only, excluding headings, JSON, evidence, calculated findings and disclaimers. `report.text` is a readable combined report with calculated findings clearly separated from AI interpretation. Identical normalized paragraphs and under/over-length sections are rejected; the application does not add padding, truncate to hide a failure, or silently fall back to brief mode.
- Defaults: `ASTRO_AI_ENABLED=true`, `ASTRO_AI_BASE_URL=http://127.0.0.1:11434`, `ASTRO_AI_MODEL=qwen2.5:7b`, `ASTRO_AI_TIMEOUT_SECONDS=90` per generation (valid range 1–180), `ASTRO_AI_REPORT_TIMEOUT_SECONDS=900` for the detailed report (valid range 30–1800). Detailed chapters are generated sequentially with 2,048-token budgets and at most two validation retries each; the overall deadline bounds the whole generation. The synchronous HTTP caller/proxy needs a timeout suitable for the configured report deadline. Set `ASTRO_AI_ENABLED=false` to disable reports without disabling calculations.
- Only literal loopback addresses or localhost are allowed; redirects and proxies are disabled. Ollama must already be running and the model must already be installed. Model metadata is checked to reject cloud aliases. There is no download, cloud fallback, or hosted-model API key.
- The model receives only topic, opaque reference aliases, polarities and server-generated non-technical summaries of the calculated rules. Original indicators and selected calculated facts (house/sign/lord/dignity/points) are returned separately as evidence, not rewritten by the model; model references are mapped back to original IDs. Raw birth inputs, names, free-text questions, and full charts are excluded. Prompts/reports are not logged or persisted by the application. This is data minimization, not a claim of anonymization.
- Reports have a fixed disclaimer and `aiGenerated=true`. AI prose is limited to non-technical reflections: reject numbers, markup, listed planetary/sign/placement terms and common certainty words. Schema validation checks section structure, reference IDs, and supporting/conflicting polarity coverage; repeated valid IDs are deduplicated. These checks cannot prove factual entailment or predictive validity. Treat returned text as plain text, not trusted HTML.
- AI uses a separate one-request concurrency limit, a bounded HTTP body and generation timeout. Responses are 503 for disabled/busy/unavailable local AI, 504 for timeout, and 502 for invalid model output; existing calculation endpoints do not call Ollama.
- AI regression tests are part of `mvn -o -B -ntp verify` and use mocks plus a local fake HTTP server; they do not require Ollama. Run `mvn -o -B -ntp -Dtest=AiReportLiveTest -Dastro.ai.live=true test` for the opt-in live local-model test using a synthetic birth fixture. It requires the Python worker and installed model and is skipped by default. Also smoke-test the HTTP report endpoint before deploying.
- The current Dockerfile still lacks the Python worker; loopback Ollama access is for host-local execution, not an unconfigured multi-container deployment.

# Self-hosted geocoding

- `POST /api/astro/v2/locations/search` accepts `city`, optional `state`, `country`, and optional two-letter `countryCode`. Example: `{"city":"Munger","state":"Bihar","country":"India","countryCode":"IN"}`. No birth date or time is required or sent to the geocoder.
- Set `ASTRO_GEOCODER_URL` to the base URL of your own Nominatim instance. It defaults to empty (search returns 503 until configured). `ASTRO_GEOCODER_TIMEOUT_SECONDS` defaults to 10 and supports 1–30. Public nominatim.openstreetmap.org is explicitly rejected; no paid/public fallback is used. Proxies and HTTP redirects are disabled.
- Results contain up to five candidates, each with coordinates, display name, OSM ID/type, address components and a timezone when resolvable. `selectionRequired` is a caller/UI confirmation signal, not automatic selection. After confirmation, copy the candidate's latitude, longitude and timezone into the existing v2 `birth` object. Legacy city-only endpoints still use the hardcoded Indian-city list.
- State is optional because administrative hierarchies differ worldwide. Do not treat provider order as certainty or silently use the first candidate. City points are representative, not hospital-level coordinates. Coverage depends on the OSM data imported into the configured server.
- Timezones are resolved offline using the existing Python worker's `timezones` action and timezonefinder polygons. Missing/unavailable zones are returned as null with `status=partial`; never default an unknown international location to Asia/Kolkata. Historical UTC offsets remain the responsibility of `birth_input` and IANA ZoneInfo rules.
- The service allows two active searches, bounds provider response sizes and caches at most 256 complete searches for 24 hours in process memory. Results include OpenStreetMap attribution and ODbL information; display attribution in any consuming UI.
- Optional Compose profile `geocoding` provides a digest-pinned `mediagis/nominatim:5.2` image, loopback HTTP port 18081 (override `ASTRO_GEOCODER_PORT`) and persistent `nominatim-data`. No PostgreSQL port is published. `IMPORT_STYLE=admin` imports administrative boundaries and places, not detailed street/POI data. Optional external dumps and automatic replication are disabled.
- The profile requires a public HTTPS `NOMINATIM_PBF_URL`, `NOMINATIM_PASSWORD` supplied outside version control, and explicit `NOMINATIM_ALLOW_INITIAL_IMPORT=true` for a first import. After selecting the dataset and confirming resources, the owner can start it with `podman compose -f podman-compose.yml --profile geocoding up -d nominatim`. No import has been performed or actual Nominatim container startup verified in this workspace.
- An initial import may reinitialize the Nominatim database if its completion marker is absent. Never enable reimport on an existing populated volume or delete database volumes without explicit approval. Configure dataset updates separately before relying on long-term freshness.
- Host Java can use `ASTRO_GEOCODER_URL=http://127.0.0.1:18081`; a backend container on the Compose network can use `http://nominatim:8080`. The current backend image lacks Python, so offline timezone resolution in that image is unavailable until worker packaging is added; coordinate search can return partial results with an explicit warning.
- `worker/nominatim-no-trace.bash` must be mounted read-only and referenced by `BASH_ENV`: upstream startup scripts enable shell tracing, which could expose the database password. Podman Compose 1.5.0 ignored inline config content during dry-run testing, so this is a real bind-mounted guard file. Do not remove this guard.
- Geocoding tests use a local HTTP stub, not the public Nominatim service. Python tests verify timezone lookup for Munger, New York, Sydney, London and Singapore. An end-to-end HTTP smoke test verified a stubbed Munger result through the real timezone worker into a real natal calculation. Compose configuration and dry-run mounting were verified without downloading/importing map data.
- Full standard planet imports are large server operations (Nominatim recommends 128 GB RAM and at least 1 TB disk); reduced import styles can differ. Do not automatically download/import worldwide data on a developer machine. The optional profile does not establish worldwide coverage by itself.
- If Homebrew tools are absent from the shell PATH, use `/opt/homebrew/bin/mvn` and `/opt/homebrew/bin/podman-compose --podman-path /opt/homebrew/bin/podman`; do not modify global shell or Git configuration.
